# P2P 心跳与掉线重进验证

## 结论与修复

2026-10-23 玩家诊断包中，访客在同一会话内累计建立并关闭了 511 条游戏/状态探测流，随后新游戏连接无法继续创建，退出房间后重新分配会话才恢复。桥此前从 3 开始每次加 2 分配 SCTP 流编号，与实际协商的 1023 上限相遇。这能解释“掉线后无法重进”，不能据此认定最初那次掉线的原因。

现在由 libdatachannel 分配、回收 SCTP 编号。单次创建失败只让该新连接走中转，保留其他游戏流，并记录 `peer_stream_fallback`。

截图提醒的“死连接”也已专项处理。此前并非完全没有心跳：SSH 有 5 秒探测/20 秒超时，P2P 库启用 ICE/STUN 存活检测和 SCTP 心跳。新增的是桥自身的 P2P 应用层探活、明确的超时日志以及同一房间内的降级和直连恢复。

| 场景 | 处理 |
| --- | --- |
| 空闲直连 | 每对玩家一条控制通道，每 5 秒 ping/pong，20 秒没有有效 pong 判失效 |
| 旧版桥 | 最多 3 次能力探测；不支持者保留库层存活检测，避免新心跳误判 |
| 单向丢包 | 仅收到 ping 不能续命，必须收到自己探测的有效回复 |
| 一名玩家直连失效 | 关闭该玩家的失效直连流；健康 SSH、房间、监听端口和其他玩家保留 |
| 网络恢复 | 信令可用时退避重试直连；新连接恢复直连，已有中转流不强行迁移 |
| 信令子通道关闭/写失败 | 隔离到信令处理，不作为整个 SSH 连接失效 |
| SSH 也失效 | 进入原有房间重连/备用节点流程 |

已经断开的 Minecraft TCP 连接需要在游戏中重新连接，无法保证那条连接的无缝恢复；无需先退出启动器房间。双方都升级后才启用新的应用层心跳。

## Ubuntu 验证

测试在服务器的 `/tmp/buggcraft-native-validation` 独立目录进行，没有替换生产服务。使用 Release C++ 核心、桥进程和通过公开 C ABI 加载 `.so` 的 Python 调用方；后者每个客户端独立进程，避免进程级日志目录互相影响。

- `ctest`：两个目标通过，包含原生心跳状态机和纯 C ABI 消费者。
- 专项集成：8 项通过，EXE/动态库各运行下列 4 个场景。
- 核心、桥、动态库服务、节点健康、日志和选路回归：54 项中 51 项通过。两项因服务器没有相邻启动器源码跳过，一项因未配置 `BUGGCRAFT_LAUNCHER_SDK` 跳过。

| 用例 | 必须满足的断言 |
| --- | --- |
| 空闲 32 秒 | 超过 20 秒期限后仍为直连；日志有至少 4 次有效 pong 与 RTT；恢复游戏传输成功 |
| 单向 UDP 黑洞 | 只丢房主→访客的 UDP，SSH 正常；另一名玩家持续传输；故障玩家转中转后可重连 |
| 同一会话恢复直连 | 恢复 UDP 后自动协商；SSH 身份和本地端口不变；已有中转流持续回显，新流为 P2P |
| 信令关闭 | 主动关闭一名访客的信令；其游戏能中转，另一访客继续直连，SSH 身份不变 |
| 编号耗尽回归 | 保持长流并连续建立 640 次短连接；RST 长流后同房间再进 3 次；检查编号复用且测试阶段没有偷偷转中转 |

UDP 黑洞通过测试专用双向 UDP 代理注入，DTLS/SCTP 仍由真实桥处理，未调整防火墙。该负载下底层传输约十几秒先发现失联，随后桥降级；不能将这个结果写成“实测应用心跳恰好 20 秒超时”。20 秒边界、重放、畸形帧、旧版兼容和限频由 C++ 状态机测试单独验证。

测试是 TCP 回显与协议集成，不是本版本的 Minecraft GUI 实测，也不是重新完成了 30 分钟吞吐压测。历史原版游戏和长压结果见 [性能与验证](../performance.md)。

## 平台与日志

Windows 已完成 Release 构建、两个 CTest 目标。最终动态库专项 6 项全部通过，耗时 94.602 秒：多 handle 并发、中文/空格安装路径、640 次短连接与游戏复位重进、空闲心跳、单向丢包后恢复直连、信令关闭隔离。首次 ICE 协商有间歇性超时，测试等待并要求自动重试后确实恢复 P2P，不能以中转通过直连断言。随后修正大联邦拓扑发现，再次构建并安装完整运行目录，2 个 CTest 和 7 项 DLL ABI/路径/选路回归通过；交付压缩包使用该最终构建。

独立桥 EXE 曾被本机应用程序控制策略以 WinError 4551 拒绝启动；不修改系统策略，也不把受阻场景记为通过。Ubuntu 的桥进程与动态库均通过。macOS 需要对应 CI/实机结果，不以 Ubuntu 结果替代。

原始专项日志、逐玩家 JSONL 和回归日志保存在本机 `validation-artifacts/peer-heartbeat-ubuntu-20261024/`；Windows 在 `validation-artifacts/peer-heartbeat-windows-20261024/`。这些目录不提交公开仓库，避免公开玩家网络元数据。公开结果见 [测量记录](../measurements/peer-recovery-20261024.json)。

客户端需更新完整原生运行目录并重启启动器。只部署服务器不能替换玩家机器中的旧桥；Windows 应保留 `bin/buggcraft_bridge.dll` 及其同目录依赖，不能只散发一个 DLL 或混入 Qt 目录。

## 复现

在完整安装并设置 `BUGGCRAFT_NATIVE_CORE`、`BUGGCRAFT_BRIDGE_EXECUTABLE`、`BUGGCRAFT_BRIDGE_LIBRARY` 后：

```bash
ctest --test-dir build --output-on-failure
BUGGCRAFT_BRIDGE_SOAK_LOG_DIR="$PWD/validation-artifacts/peer-recovery" \
  .venv/bin/python -m unittest tests.test_peer_heartbeat tests.test_peer_reconnect -v
```
