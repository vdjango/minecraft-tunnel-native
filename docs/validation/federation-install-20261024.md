# 联邦扩容与 Ubuntu 安装验证（2026-10-24）

## 结果

联邦不再限制为 32 个成员。成员总数与每次交换的大小分别处理：成员目录可继续增长，单次同步分页，每节点仍最多 3 个在途交换和 3 条出站连接。没有固定成员上限不等于机器有无限容量。

原生桥还存在另一处 32 节点判断：拓扑超过 32 项时，整份备用入口被忽略。65 节点故障测试发现了这个问题，现已修正。客户端发现接口支持分页；桥只获取少量候选，实际探测仍有并发和数量预算。

Ubuntu 安装包已在独立 Ubuntu 24.04 容器中通过实际 `apt` 安装和重装，提供专用服务账号、systemd unit、网页初始化和 `buggcraft-node setup/status/logs` 命令。安装时不运行 pip；目前没有在线 APT 软件源。

## 联邦测试

在 Ubuntu 24.04 x86_64、4 vCPU、约 3.7 GiB RAM 的同一台服务器上运行真实 C++ 核心和桥。使用独立端口、目录和测试身份，没有替换生产服务。完整组合运行 35 项，34 项通过，1 项因未配置启动器 SDK 跳过，共 247.800 秒。

| 场景 | 断言与结果 |
| --- | --- |
| 130 个签名成员 | 邀请及签名目录全部接纳，超过旧的 32 成员限制 |
| 分页同步 | 重建全部成员；请求小于 16 KiB，每页最多 32 条；不变记录不重复发送 |
| 客户端拓扑分页 | 129 个其他成员分批读取，每次最多 5 项，响应低于原生 RPC 大小限制 |
| 1000 个调度对象 | 每轮最多 3 个交换，发现调度没有永久遗漏成员 |
| 1000 个账号操作 | 最多 3 个工作协程，取消后没有残留任务；这是调度测试，不是 1000 台真实节点 |
| 3 节点退出和强杀 | 存活节点之间连续传输通过 |
| 17 节点长链 | H 强杀后既有连接、新房间、直查和备用入口通过 |
| 65 节点长链 | H 强杀后既有连接和新房间通过，最终 64 个幸存成员互相可见；原先选中 H 的客户端恢复备用入口 |

65 节点从 A 经 31 个成员到 H，再经 31 个成员到 Q。完成发现后强杀 H；Q 查询本地已同步目录，桥直接连接房主所属 A，不沿邀请路径逐跳询问或转发游戏流。已有数据流跨过 30 秒失效租约继续校验，故障后创建的新房间也能传播、解析和加入。

| 测量 | 17 节点 | 65 节点 |
| --- | ---: | ---: |
| 初次成员和账号目录收敛 | 4.531 s | 27.525 s |
| 64 KiB 回显块 RTT p99 / 最大值 | 11.086 / 54.064 ms | 313.135 / 378.620 ms |
| 已同步好友查询额外远端补查 | 0 | 0 |
| 已同步好友 SSH 请求最大耗时 | 170.134 ms | 1891.352 ms |
| 原入口故障后首次目录恢复 | 0.135 s | 1.977 s |
| 后续加入房间 | 0.090 s | 1.479 s |
| 最终互相可见的幸存成员 | 16 / 16 | 64 / 64 |

65 个实例共享同一台主机时延迟明显上升，租约观察期间单个节点最少看到 63 个在线成员，最终收敛为 64。不能将这些结果描述成“全程目录没有抖动”“低延迟无限扩展”或公网玩家容量。故障后整个验证流程持续 67.500 秒，包含传输、查询、新房间传播与备用入口验证；它不是 67.500 秒的满速吞吐测试。

本轮使用 TCP 回显校验载荷，没有重新运行原版 Minecraft GUI 或 30 分钟压力测试。成员之间需要实际网络可达并完成发现；若失联的是房间实际承载节点，活动中转流无法依靠更换目录入口无缝迁移。

## 安装包测试

测试包为 `buggcraft-node_2026.10.24.2_amd64.deb`，从实际 CMake 安装目录构建。测试仅使用包内程序和私有依赖，没有依赖源码目录或开发虚拟环境。

- `apt-get install` 安装成功，专用账号能够启动 Web 和原生核心。
- 初始化链接文件权限为 `0600`，无 token 请求被拒绝；CLI 显示的证书指纹与实际 TLS 证书相符。
- 网页提交配置成功，初始化链接删除，原生 SSH 固定公钥认证及目录 ping 成功。
- 实际 `apt-get --reinstall` 后再次启动成功，节点主机密钥不变，不重新进入初始化。
- `systemd-analyze verify` 通过。容器中的服务由专用用户直接启动，没有验证以 systemd 为 PID 1 的开机流程。

首次包测试暴露了初始化链接写入时缺少 `json` 导入，已修正后重新构建；失败包不作为交付产物。

Windows 最终 Release 构建与 2 个 CTest 目标通过。拓扑修改后，另用 DLL 跑了 7 项 ABI、中文/空格安装路径和选路回归，全部通过，耗时 9.898 秒。完整心跳故障测试见 [心跳与重连验证](peer-recovery-20261024.md)。macOS 需对应 CI/实机验证。

公开数据见 [测量 JSON](../measurements/federation-install-20261024.json)。原始组合日志、安装日志和 66 份逐玩家/运行日志归档留存在本地 `validation-artifacts/federation-install-20261024/`，不上传公开仓库。

## 复现

构建并安装 Release 原生运行目录，设置 `BUGGCRAFT_NATIVE_CORE`、`BUGGCRAFT_BRIDGE_EXECUTABLE` 和 `BUGGCRAFT_BRIDGE_LIBRARY` 后：

```bash
BUGGCRAFT_FEDERATION_SCALE=1 \
  .venv/bin/python -m unittest tests.test_federation_budget tests.test_federation_scale \
  tests.test_federation_lookup tests.test_federation_resilience \
  tests.test_federation_chain tests.test_route_selection -v
python3 scripts/build_deb.py --runtime runtime --version 2026.10.24.2
```

包安装和重装测试应使用可丢弃的 Ubuntu 24.04 环境，具体命令见 CI 的包安装步骤。已有手动部署的生产节点继续使用原有 unit 和数据路径升级，不直接在其上覆盖安装新包。
