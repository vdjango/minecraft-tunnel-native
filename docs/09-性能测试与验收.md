# 性能测试

## 2026-11-11 成都双栈修复

扩展既有 Engine::stun：IPv4-mapped IPv6 来源按 IPv4 返回地址并使用 /24 限频桶，避免所有 IPv4 请求落入同一 IPv6 /64 桶；IPv6 UDP 显式尝试双栈。补测复现 Windows `::` 的 TCP 默认 IPv6-only，Engine::run 对该通配地址显式创建双栈 TCP 监听，移交 libssh 所有权。复用 socket、libssh、已有 STUN 编码和限频，不增加新的传输或直连规则。

Windows Release 上 IPv6 SSH/STUN、双栈地址族、实际载荷/半关闭三项通过；成都 x86_64 Linux Release 的原生核心分别验证 IPv4/IPv6 回环映射正确。核心部署为待接通产物，不启动遗留 Python 适配器。独立公网 TCP/UDP 3333 的 IPv4/IPv6 均超时，尚不能宣称成都中继或公网打洞已通过；未打开游戏。分发与带宽三轮原始结果及域名延期见相邻源站 [成都报告](../../bugg-source/文档/35-成都分发与完整房间缓存.md)。该修复是协议正确性，不报 SIMD 或游戏提速倍率。

游戏转发由 C++ 节点核心和原生桥执行。性能取决于 CPU、加密算法、网络、同时连接数和 Minecraft 活动；发布包通过测试不等于某台服务器可以承载固定数量的玩家。

新增 ISA 分派、复用边界与对照命令见[跨架构性能优化](10-跨架构性能优化.md)；本次同机五轮的整理结果见[性能实测报告-20261110](30-性能报告/01-20261110-跨架构与CPU实测.md)，其中区分新代码收益、SIMD 开关与 OpenSSL 原有加速。

文件下载期间的游戏小包与新版启动器请求调度另见[协同优化实测](30-性能报告/02-20261110-文件与游戏协同实测.md)。复用 `scripts/bridge_soak.py --scenario mixed --file-mib 16`，四个文件校验 SHA-256，独立游戏连接验证回声/EOF；默认关闭发生器调试，保留三轮前后交替结果及资源采样。

## 测量方式

当前节点默认关闭额外中继压缩，配置及取舍见 [11-转发性能与压缩配置](11-转发性能与压缩配置.md)。早期报告中的“默认压缩”指当时的 auto；为保持负载可复现，压测必须显式选择 off/auto，不能把配置变更当成新性能数据。

游戏载荷加密路径与硬件开关的三轮对照见[游戏转发指令集实测](30-性能报告/03-20261110-游戏转发与加密指令集.md)。`scripts/benchmark_forwarding.py` 复用原生桥持续负载，默认三位玩家、每人两条不限速大流和独立小包探测，并输出实际 SSH cipher、吞吐、P99 和采样 CPU 秒/GiB。`--compression off` 隔离加密，`--compression auto` 覆盖可选压缩路径；`--profiles` 可分别验证旧代码、新字节 SIMD 与 OpenSSL 硬件加速，不应混成同一倍率。

比较实现或配置时，应固定源码版本、构建参数、加密算法、压缩策略、连接数和数据量，至少运行三轮，记录中位数和范围。

| 测试 | 关注指标 | 入口 |
| --- | --- | --- |
| 节点中转 | 已校验应用载荷吞吐、CPU 时间、峰值 RSS、回声 RTT | `scripts/benchmark.py` |
| 持续负载 | 吞吐时间窗口、RTT p50/p99/最大值、数据块最大间隔、断流与 EOF | `scripts/bridge_soak.py` |
| A 建房 / B 加入 | 建房、加入、首次收发及重连耗时 | `scripts/vanilla_player_pair.py` |
| 多玩家原版游戏 | 进服、移动、方块同步、死亡复活、断线后重进 | `scripts/vanilla_multiplayer.py`、`scripts/vanilla_player_pair.py` |
| 联邦故障 | 中间节点退出后目录查询、新房间加入及既有连接 | `tests/test_federation_chain.py`、`tests/test_federation_resilience.py` |

回环吞吐不是物理网卡线速；同机 RTT 不能代表公网延迟。应用载荷字节也不同于包含 SSH、TCP、UDP 和重传的网卡流量。压缩收益应同时记录原始字节、编码字节和 CPU；不能用重复字符串压测推算 Minecraft 的实际节省比例。

## 持续负载

按[构建指南](02-构建与发布.md)安装完整原生运行目录及测试依赖，在 Ubuntu 的仓库根目录运行：

```bash
export BUGGCRAFT_NATIVE_CORE="$PWD/runtime/bin/buggcraft-core"
export BUGGCRAFT_BRIDGE_EXECUTABLE="$PWD/runtime/bin/buggcraft-bridge"

# 30 分钟，3 位访客，每位 3 条不限速大流，另有延迟探测和短连接
.venv/bin/python scripts/bridge_soak.py --seconds 1800 \
  --bulk-streams 3 --bulk-rate 0 --output validation-artifacts/bridge-soak.json
```

该负载不是 Minecraft GUI 游戏。原版游戏验证还需要合法游戏资源、匹配的 Java 和图形环境；应单独检查死亡复活、房间重进、连续游玩和多人同时操作。

专用 `bridge_soak.py` 默认关闭负载发生器的 asyncio 调试；`--asyncio-debug` 可显式开启做诊断，普通 unittest 回归仍使用原来的调试默认。输出同时记录 `asyncio_debug` 与 `requested_asyncio_debug`。调试模式会为高频任务/网络回调收集额外诊断信息，不要把两种驱动配置混为同一负载，或将关闭驱动调试的收益归因于原生节点代码。

运行前检查脚本的 `--help`，使用独立端口和目录，并确认机器有足够资源与带宽。回归必须同时校验数据内容与结束 EOF，不能仅统计平均吞吐；短暂停顿应通过最大延迟、分位数和时间窗口暴露。

## 结果留存

原始测量 JSON、截图、逐玩家日志和排查记录保存在本地 `validation-artifacts/`，不提交到源代码仓库。整理后不含凭据与玩家隐私的报告可放在 `docs/` 并加入索引；附源码版本/工作区快照、构建参数、机器与依赖版本、测试命令和统计口径。

[GitHub Actions](https://github.com/vdjango/minecraft-tunnel-native/actions/workflows/core.yml)提供 Windows、Ubuntu、macOS ARM64/Intel 的构建与自动回归结果。CI 的短时多连接测试用于发现回归，不能替代公网实测或 30 分钟连续负载。压缩策略与限制见[中转压缩](20-协议规范/07-中继压缩扩展.md)。
