# 桥入口与依赖体积实测

日期：2026-11-11。范围：Windows x64 隔离构建与运行验证，不是生产发布。本文 MB 均为十进制；比较包含依赖的完整目录，而非只比较主文件。此轮测体积和正确性，没有测游戏性能增益。

## 当前启动器怎样调用桥

新版启动器的 `NativeBridge`（`bugg/src/modules/multiplayer/infrastructure/native_bridge.cpp`）通过 **QProcess 启动独立原生桥**，用换行 JSON-RPC 收发控制命令，没有加载 C ABI 动态库。游戏载荷由桥内 Session/网络线程转发，不经 QML 或进程标准输入输出传输。

项目已有另一种入口：Windows DLL、Linux SO、macOS dylib，见 [SDK 接入](../06-原生桥与SDK.md)。CLI 和 C ABI 共用 `buggcraft-bridge-engine`、Rpc、ControlClient 和 Session，没有另写联机实现。C ABI 当前仍接收 JSON；直接换 DLL 不会自动消除 JSON，也不能由此推导游戏延迟下降。

## 同一套构建实测

桥使用既有隔离 MinGW 15.2 构建，`-Os -ffunction-sections -fdata-sections`、链接 GC、strip；该构建 LTO 关闭，原因是此前 GCC 15.2 C++ LTO 内部编译错误。不得将其描述为新算法或 SIMD 提速。Qt 主程序是上一轮自编 Qt 6.8.1 / MSVC 19.44 静态研究包，保持原字节。

| 交付形式 | 入口文件 B | 连同依赖解压 B | ZIP B | 7z B |
| --- | ---: | ---: | ---: | ---: |
| 原精简 EXE 桥 | 1,758,573 | 16,627,865 | 6,755,736 | 4,590,254 |
| 原精简 DLL 桥 | 1,755,788 | 16,625,080 | 未重新归档 | 未重新归档 |
| 本轮依赖裁剪后 EXE 桥 | 1,758,573 | **13,239,961** | **5,141,961** | **3,496,773** |
| 本轮依赖裁剪后 DLL 桥 | 1,755,788 | 13,237,176 | 5,140,296 | 3,495,814 |

两种入口仅差 **2,785 B**；最终完整 7z 只差 **959 B**。入口不同，SSH、WebRTC、加密、C++ 运行库照样存在。只把 EXE 改成 DLL/SO，无法把这部分功能的体积消掉。

CLI 和 SDK 是替代入口，玩家启动器只带 CLI；不应将两种入口、节点主程序和开发包同时塞进玩家安装包。Linux 可以利用已有系统共享库降低下载增量，但这不代表加密和转发实现不占空间，也不能套用 Windows 测量值。

## 本轮真正省下的内容

原 `libcurl-x64.dll` 为 3,716,608 B，版本字符串显示它内部还有 LibreSSL、HTTP/2、HTTP/3/QUIC、SSH2、Brotli、zstd 等；桥另外已经带了 OpenSSL。实际桥只在 `profile_exchange.cpp` 用 curl 做 URL 校验和有界 HTTPS JSON 请求，没用这些额外协议。

新增唯一构建配方 [packaging/bridge-curl/CMakeLists.txt](../../packaging/bridge-curl/CMakeLists.txt)：仅为桥构建 HTTP(S) curl，**复用 SSH/WebRTC 已有的 OpenSSL**。裁去其他协议、文件传输接口、内容压缩后端及未用能力，保留 IPv6、线程 DNS、HTTP(S) 代理、IDN、证书/主机名校验和每请求自定义 CA。桥业务入口继续强制 HTTPS、禁止重定向。此配置不能用于启动器通用资源下载器。

最后运行包的 curl 是 **328,704 B**；整个桥目录减少 **3,387,904 B（20.37%）**，7z 减少 1,093,481 B（23.82%）。没有删除 OpenSSL 汇编/CPU 分派，没有更改 SSH、DTLS、数据转发、压缩协商或会话算法。

曾尝试 Schannel，DLL 更小，但在真实 `bridge::https_json` 测试中，私有 CA 没有吊销信息时返回证书吊销状态未知。因此采用 OpenSSL 方案；没有关闭证书或主机名校验绕过问题。最终通过版本是 `libcurl/8.23.0 OpenSSL/3.5.2 WinIDN`。

## 验证及边界

环境：Windows x64，Intel i9-10850K（10 核/20 线程），同机本地回环；原生桥/节点、libssh 和 libdatachannel，测试控制器使用开发环境 Python，不随产品发布。

- **9 项集成回归通过，0 失败、0 跳过**：无压缩载荷与 EOF、P2P/relay 混用、固定身份与帧预算、多个 C ABI 句柄并发/重复释放、DLL 双端联机、DLL 与 EXE 主客交叉组合、两种入口的文件哈希失败与取消回收。日志 `recipe-regression.log`，33.241 秒；外部 STUN 出现本机 socket 10013 日志，本机 ICE/P2P 状态断言和载荷测试通过，不等于公网打洞验收。
- **6 项真实 HTTPS 实现检查通过**：私有 CA 且保留 native CA 标志成功、不可信根拒绝、错误主机名拒绝、302 不跟随、262,144 B 响应上限、非 200 状态拒绝。探针直接链接既有 bridge engine 并调用 `bridge::https_json`，不是另造网络实现。未把测试 CA 加入系统信任库。
- 扫描 PE 普通/延迟导入，EXE/DLL 各自都是 9 文件闭包，无非系统缺失依赖、无多余运行库；EXE 在无开发工具 PATH、无关工作目录下初始化成功。
- 对最终 `launcher-recipe` 执行本机 Defender 扫描，返回 0、未发现威胁。未签名/未公证，不代表其他引擎、未来特征库或 SmartScreen 的结论。
- 配方从配置、构建到 `--install --strip` 已执行通过；没有覆盖 `bugg/build/bugg.exe`，没有修改生产桥/线上服务。当前依赖替换研究包保持旧导入名 `libcurl-x64.dll`；后续正式构建应通过新 `CURL_DIR` 导入并重链接，按实际导入闭包发布，不能混用任意版本 DLL。
- 没有重新执行启动器全部 Qt/UI 验收；Linux/macOS/ARM 此轮未构建，没有用 Windows 体积冒充这些平台结果。也没有用体积检查代替完整游戏性能基准。

## 复现与原始证据

构建前提：同一工具链的 OpenSSL、CMake 3.24+ 和 C 编译器。普通玩家不需要这些工具。

```sh
cmake -S packaging/bridge-curl -B build/bridge-curl -DCMAKE_BUILD_TYPE=MinSizeRel -DOPENSSL_ROOT_DIR=<与桥一致的OpenSSL前缀> -DCMAKE_INSTALL_PREFIX=<独立安装前缀>
cmake --build build/bridge-curl --config MinSizeRel --parallel 4
cmake --install build/bridge-curl --config MinSizeRel --strip
# 配置桥时传入 -DCURL_DIR=<独立安装前缀>/lib/cmake/CURL
# MSVC 使用对应生成器及相同架构；静态发布须保留依赖许可证和重新链接材料。
```

curl 固定官方 `8.23.0` 归档，SHA-256：`8dadd7d2536a314f982ad05a651b713f426bf7d02cc2c76cffb9796f2218e6c5`；本机归档 2,990,916 B 与此一致。经 HTTPS 获取并核验内容哈希，未执行独立 GPG 签名验证。配方允许使用 CMake 标准 `FETCHCONTENT_SOURCE_DIR_BRIDGE_CURL_SOURCE` 指定已验证离线源码；本轮命令保存在 `recipe-commands.json`。

## 后续怎样继续缩小

优先保留独立桥，继续统一工具链并验证静态链接/段裁剪。现在剩余 OpenSSL 6,871,539 B、MinGW 运行库 2,554,368 B、libdatachannel 1,292,295 B，才是大头。将桥和启动器统一到 MSVC 有机会复用启动器已有 CRT，再对 SSH/WebRTC/OpenSSL 采用一致静态构建和链接裁剪；需要实际测完整包，不能先声称能省掉整个库，也不能删除必要密码算法、汇编或 P2P。

若未来需要彻底去掉独立桥文件，可以将**同一个静态 bridge engine**链接进启动器；这比把 EXE 简单换成导出完整接口的 DLL 更可能获得跨模块裁剪。但引擎代码仍然存在，且会失去进程崩溃隔离。C ABI 同步调用必须放专用工作线程，销毁不得与调用竞争、返回值必须由原库释放；现有超时强杀语义也要重新设计。因此本轮没有为不足 3 KB 的入口差异重写启动器桥适配器。
