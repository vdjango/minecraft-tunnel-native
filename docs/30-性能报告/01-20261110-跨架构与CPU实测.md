# 节点、原生桥与 SDK 性能实测（2026-11-10）

本次完成共享编码/摘要重构、运行时指令集分派及可关闭的通用实现。三个 x86-64 实机上，64 KiB IPC Base64 解码相对同代码通用路径提高 **6.81–8.09 倍**，相对任务开始时实现提高 **25.26–26.91 倍**。这些是编码模块的吞吐，不是游戏帧率、玩家容量或公网速度。Linux 实际中继在本负载下没有可辨认的新 SIMD 吞吐提升；现有 OpenSSL 硬件加速对加密成本的影响更大。

**验收边界：** Windows/Linux x86-64 已实测；Xeon 上实际执行了 AVX512BW 测试。补测完成 ARM64/NEON 的交叉编译与 QEMU 正确性检查，以及模拟无 AVX 的 x86-64 自动回退。macOS、ARM64、32 位及其他架构仍没有实机性能数字，不能标为全部架构验收完成。已找到独立网卡测试端点并完成 Windows↔Linux **直接公网中继**收发；跨 NAT P2P 未建立，auto 正确回退中继。原 Windows 持续负载高尾延迟经三轮交替对照确认主要来自 unittest 默认开启的 asyncio 调试负担；改进测量驱动后的 180 秒 p99 约 4 ms，不是原生二进制发生了数百倍提速。

## 实现及复用范围

优化对象为 `core/`、`bridge/` 及它们共用的 C ABI SDK 引擎。没有修改启动器运行代码、替换生产节点或改变生产密码/系统性能参数。

| 改动 | 唯一实现与调用方 | 实际作用 |
| --- | --- | --- |
| Base64/URL/hex 与字母表检查 | `core/encoding.*`；IPC、SSH 接入码、social、profile exchange 复用 | 严格 IPC padding/尾部零位检查保留；桥各格式原有接受策略与错误码保留 |
| SIMD 扫描与实际编解码 | `core/encoding_simd.cpp`；固定版本 aklomp/base64 0.5.2 | SSE2/AVX2/AVX512BW 扫描、AArch64 NEON 扫描；AVX2/NEON64 编解码复用上游库，未复制算法 |
| 编解码并发分派 | `encoding.cpp::selected_codec` | 初始化一次不可变函数表，每次调用独立流状态，绕过上游公共接口的可变全局分派 |
| 流式哈希 | `core/digest.*`；feedback/modpack 复用 | 检查 EVP 错误、RAII 释放；文件单遍流读取；只需要 SHA256 时省去 SHA1；传输增量哈希使用同一类 |
| 清单哈希 | `bridge/modpack.cpp::catalog_hash` | 模组和资源包复用排序、序列化及摘要规则，避免两个实现漂移 |
| 构建 | `cmake/NativeCpu.cmake` | 独立 ISA 对象，检查 CPU 与 OS 状态后分派，隔离跨 ISA IPO；默认 Release，保留已有 O3/O2/LTO |
| 开发维护 | `AGENTS.md`、项目 Skill、方法/DOM 清单及 AST 生成器 | 新增前搜索唯一所有者；声明/定义/回调、Vue 模板及选择器可检索；CI 检查过期 |

没有全局加入 `-march=native` 或 `/arch:AVX2`。普通发行入口仍使用目标架构基线，不支持的硬件走通用路径。自动扫描目前优先 AVX2；AVX512BW 只从明确支持的测试/基准入口执行。MSVC AVX512 额外检查 CD/DQ/VL 与 XCR0。第三方 AVX512 Base64 需要不同的特性组合，本次没有启用。

OpenSSL 已有 AES/SHA 硬件分派；下面的加密对照是验证既有库能力，不计为本次新写代码的收益。游戏载荷通过原生转发路径，不经 Python 管理 IPC，因此不能将 Base64 数字直接映射为中继增速。

## 防火墙与跨机器验证

用户提醒后核对 Windows UIAutomation 桌面顶层窗口，未检测到待确认的安全/防火墙窗口；查询系统入站规则，当前 `build/buggcraft-core.exe`、`build/buggcraft-bridge.exe` 以及承载 C ABI SDK 的 Python311 均已有启用的 TCP/UDP Allow 规则，适用当前 Public 网络。没有声称点击了一个实际未出现的按钮，也没有关闭防火墙或批量修改无关规则。

另建 Linux 独立节点监听测试端口，使用全新临时认证 token/密钥。最初随机端口及 3334 的 Windows 公网连接超时；同服务器线上 3333 与管理 SSH 可建立 TCP，线上节点未用于压测。Linux 主机 UFW 已允许 3334/TCP 与 UDP；另一个授权 Linux 环境的几个独立端口也未能连通。这只能确认这些测试端口路径受阻，不能仅凭超时断言是哪一级设备丢弃。

继续检查后找到可用端点：**服务器网卡地址上的 TCP 18443**。原服务只占用 `127.0.0.1:18443`，测试节点仅绑定另一个网卡地址；不抢占原监听、不改 nginx/生产配置。Windows 到这个独立原生节点的直接 TCP 成功，随后双向 CLI/SDK 强制中继及 auto 共 4 项载荷检查全部通过，每项 4 MiB 随机内容加握手，校验 SHA256 与完整 EOF。该路径没有 `direct-tcpip` 或管理 SSH 载荷封装，SSH 仅用于控制测试进程。首次结果保存为 `wan-direct-negotiation.json`。

两次跨机器 auto 各观察 50 秒，实际状态均为 relay；日志中 STUN 选择数为 0。又临时添加仅允许本机来源访问测试 UDP 18443 的 UFW 规则，复测仍未选到可用 STUN、auto 仍回退，四项数据/EOF 检查通过；测试后精确删除该临时规则，并查询确认没有残留。原规则保持；未修改云安全组或开放任意 UDP 范围。不能把安全回退写成跨 NAT P2P 建立成功。当前直接公网中继可用，跨 NAT P2P 在该网络条件下不可用。

随后在同一个独立网卡端点执行 **3 轮四模式交替对照**，每模式每轮两种实际跨机角色，共 24 项；每项 4 MiB 随机内容+握手，哈希与 EOF 全部通过。掩码作用于新建的节点、双方 CLI/SDK 原生进程；Python 只做控制与 echo，不把管理 SSH 通道用于载荷。以下 MiB/s 是单个完整回声事务的原始输入字节/耗时，**没有乘以双向出口数**，与前面同机出口合计口径不同；只有一个流、短载荷及真实公网 RTT，不用于估计节点容量。

| 模式 | Linux SDK 房主→Windows CLI 客户端，MiB/s 中位数 (范围) | Windows SDK 房主→Linux CLI 客户端，MiB/s 中位数 (范围) |
| --- | ---: | ---: |
| auto | 0.7573 (0.7335–0.7666) | 0.7006 (0.6949–0.7454) |
| scalar | 0.7190 (0.7152–0.7252) | 0.7029 (0.6972–0.7398) |
| crypto-generic | 0.7335 (0.7130–0.7463) | 0.7279 (0.7062–0.7325) |
| generic | 0.7356 (0.7315–0.7464) | 0.7194 (0.7074–0.7556) |

该公网样本没有显示可重复的 ISA 速度优势。它证明四模式下双方当前原生实现可以完整跨机传输；不能把微基准的 8 倍套到这里。

额外通过管理 SSH 的 `direct-tcpip` 通道连接独立原生节点，完成了实际跨机器游戏载荷检查：Linux SDK 主机→Windows CLI 客户端、Windows SDK 主机→Linux CLI 客户端，各执行强制中继与 auto 两种传输策略，共 4 项，每项 4 MiB 随机载荷加 Minecraft 握手，SHA256 与完整 EOF 均通过；auto 观察 50 秒后仍为 relay，**没有 P2P 成功证据**。结果另存 `windows-linux-wan.json`。这条路径有额外 SSH 封装，只证明 CLI/SDK 在该路径上跨机互通，不声明节点直接公网可达，也不用于中继性能排名。连接探测主动关闭的辅助 TCP 套接字按现有测试夹具处理，载荷/hash/EOF 错误仍会使测试失败。

## 尚缺的验收与后续定位

1. 直接公网中继已验收；跨 NAT P2P 在目前网络条件下未建立。要覆盖成功路径，需要双方可用的 UDP/STUN 路径或另一组允许穿透的网络；目前已验证回退中继且载荷完整。
2. ARM64 Windows/Linux/macOS 及 Intel macOS 实机验证与性能对照；CI 已增加通用回退检查，但配置文件不等于 CI 已执行成功。
3. 独立多进程/多机发流，消除 AsyncSSH 单进程和同机竞争，再测容量、满负载 p99、CPU 分布及长期稳定性。Windows 初测高尾延迟已定位到发生器调试开销，不能把驱动修正归功于更宽 SIMD。
4. 当前没有 SVE、RVV、AltiVec 专用实现，也没有逐一验证所有 CPU 架构。可构建目标使用通用回退；“支持所有指令集且都已极限优化”不是本报告结论。

- `intel-baseline.json`、`intel-cpu.json`、`intel-encoding.json`、`intel-encoding-tests.log`。

- `evidence/arm64-*.log`、`arm64-encoding-tests`、`x86-no-avx.log` 是交叉编译/模拟正确性材料，不含 ARM 性能结论。

关键复现命令和四模式定义见[跨架构性能优化](../10-跨架构性能优化.md)；节点/SDK 依赖准备见[构建指南](../02-构建与发布.md)。一次最小复测：

```bash
python scripts/fetch_deps.py

ctest --test-dir build --output-on-failure

```
