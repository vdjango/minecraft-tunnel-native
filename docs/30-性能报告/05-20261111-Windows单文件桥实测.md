# Windows 单文件桥实测

2026-11-11，本机隔离研究；承接 [入口与依赖体积研究](04-20261111-桥入口与依赖体积实测.md)。用户目标是原生单文件、减少误报、尽量小且保留联机性能。本轮交付的是**桥本身一个 EXE**，没有把 Qt 启动器及全部内容合成一个 EXE。

## 实现与体积

新增默认关闭的 `BUGGCRAFT_STANDALONE_BRIDGE`，见[构建说明](../02-构建与发布.md#windows-单文件桥)。复用原有 `buggcraft-bridge-engine`、Rpc、Session、SSH/P2P、编码与摘要；没有复制第二套协议或转发。libssh、libdatachannel 及其子依赖、curl、OpenSSL、zstd、zlib、编译器运行库均静态链接。Windows 自带系统 DLL 不随包分发，也不算需要用户额外安装的依赖。

以普通 `strip --strip-unneeded` 去除符号，保留正常 PE、异常展开、安全校验、加密汇编和 CPU/OS 运行时指令集分派。没有 UPX、壳、内存加载器、自解包器或运行时释放第三方 DLL；测试、头文件、开发静态库及 Python 不进入玩家运行包。

| 同源码、同工具链比较 | 动态桥目录 | 单文件桥 |
| --- | ---: | ---: |
| 运行文件数量 | 9 | **1** |
| EXE/目录总字节 | 13,258,325 | **10,522,234** |

单文件运行体积为 **10.52 MB / 10.03 MiB**，比完整动态目录小 **20.64%**；7z 小 17.41%。仍未达到十进制 10 MB。压缩归档需要用户或安装器在安装阶段解压；**直接运行的 EXE 本身是 10.52 MB，不是 2.89 MB**。

许可证以只读字符串内嵌，`buggcraft-bridge.exe --licenses` 输出项目与依赖许可，包括 OpenSSL、LGPL libssh、GCC 运行库例外、MinGW 和 winpthreads。另生成并实际执行可重链接材料 `relink-kit/`，它属于开发附件，不进入玩家包；公开发布前还须提供准确对应源码。当前是本机研究产物，未公开发布、未替换启动器固定入口。

## 性能对照

环境：Windows x64、i9-10850K 10 核/20 线程；MinGW GCC 15.2 / UCRT，OpenSSL 3.5.2（保留汇编）、curl 8.23.0；同一份当前源码、同样 `-Os -DNDEBUG -ffunction-sections -fdata-sections`，链接 GC。既有 GCC 15.2 C++ LTO 出现编译器内部错误，两个构建均显式 `BUGGCRAFT_LTO=OFF`。OpenSSL 使用现有工具链静态库，未宣称已做自编密码算法裁剪。

同一个原生节点二进制，三名访客、每人两条不限速大流及独立游戏小包探测，经过 Minecraft 握手、实际 SSH relay、载荷校验和 EOF；每项 30 秒，动态/静态交替三轮，总计六轮。显式关闭额外压缩，实际所有传输双向均协商 `aes256-gcm@openssh.com`。复用 `scripts/bridge_soak.py`，测试控制器 Python 仅在开发机，不进入桥运行依赖。结论是本机回环合成载荷，不是公网带宽或 Minecraft GUI 游玩测量。

这六轮没有显示单文件链接带来整体性能退步，单文件中位数更好；范围重叠、桌面有背景负载，**不宣称稳定提速百分比**，也不把链接变化说成游戏 FPS 或公网延迟优化。此轮仅比较打包/链接方式，未重跑 ISA 开关对照；既有指令集结论见 [03](03-20261110-游戏转发与加密指令集.md)。曾有一组探索测量与构建重叠，已中断，留在根目录 `baseline-1*` 等；正式统计只用 `measurements/` 六项，构建完成后重新执行。

## 正确性与误报验证

- CTest 三组通过，包括 **110 个原生用例**、编码向量/边界及内嵌协议表。加密、身份固定、公钥验证、队列和半关闭实现未另写。
- 桥集成 **8 项通过、零失败/跳过**：关闭压缩载荷/EOF、限制算法协商、P2P 与 relay 混用、压缩尾部排空、错误身份/帧预算、文件坏哈希/取消、边下载边转发及控制预算。
- 对最终单文件 EXE 的 **7 项 TLS/IPv6 检查通过**：自建 CA、拒绝不可信根、拒绝错误主机名、不跟随重定向、响应上限、拒绝非 200、IPv6 自建 CA。路径是实际 `node.add -> ControlClient -> https_json`，成功 TLS 后故意给错签名公钥，确认执行到独立的固定签名校验；不把该预期拒绝写成完整控制登录通过。
- 编译后 CMake 检查非系统运行依赖，另用 PE 解析检查普通和延迟导入，结果只有 Windows 系统 DLL；临时目录、仅 System32 的 PATH 下，`--version`、`--licenses` 和 `bridge.initialize` 成功。
- `cmake --install --component bridge-runtime --strip` 仅安装一个桥 EXE；SDK、测试、节点不进入该组件。可重新链接材料实际重链接并运行版本命令通过。
- 本机 Microsoft Defender 对最终单文件扫描返回 0，未发现威胁。文件 **NotSigned**，没有开发者正式签名证书、SmartScreen 信誉验收、外部杀软结果或 macOS 公证。不能保证永不误报；不上传私有包到外部扫描站点，不关闭防护或添加排除。

保留标准原生格式、可验证来源、稳定发布和正式签名是降低分发问题的方向；不能把签名说成永久免报毒。微软说明签名信誉和下载信誉仍参与 SmartScreen，EV 证书也不再保证立即通过，见[官方说明](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)。静态链接采用[上游 libdatachannel 构建入口](https://github.com/paullouisageneau/libdatachannel/blob/master/BUILDING.md)，未修改第三方算法。
