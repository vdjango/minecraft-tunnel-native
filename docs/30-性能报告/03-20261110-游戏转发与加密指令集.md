# 游戏转发与加密指令集实测（2026-11-10）

本轮针对节点—桥—SDK 的游戏载荷热路径。新默认策略让桥在当前 OpenSSL 的 AES-256-GCM 明显更快、且小包成本没有明显退化时优先协商该算法，实际游戏转发继续使用 libssh/OpenSSL。固定无压缩负载三轮中位吞吐：Windows 119.00→126.58 MiB/s（+6.37%），Linux 152.00→183.81 MiB/s（+20.93%）。这是本轮代码前后收益；同算法屏蔽硬件的 5.58×/10.33× 是 OpenSSL 原有加速的贡献，不能称为本轮新增收益。

## 实现及复用边界

检索现有 `bridge/ssh.cpp`、`core/relay.cpp`、`bridge/stream.cpp`、`bridge/codec.cpp`、CPU 基准和 libssh 默认算法后，确认转发已经有 Ring、有界队列、公平批次、EOF 排空和不可压缩数据降级。没有为套用 SIMD 再复制转发循环、memcpy、加密或压缩算法。既有 Base64 SIMD 主要服务控制数据，关闭它在本负载中没有显示游戏转发收益。

libssh 0.12.2 的默认客户端 cipher 顺序将 ChaCha20-Poly1305 排在 AES-GCM 前。桥原先沿用该顺序，支持 AES-NI 的客户端也不会因为 AES 更快而自动改选。新增 `bridge/cipher_policy.*` 是唯一策略所有者；CLI 与 C ABI SDK 共用 Ssh 入口，在 connect 前向库允许列表前置偏好，保留所有库默认回退。成功连接记录实际双向 cipher，节点共用诊断也补该字段。

首次连接用合成数据，通过 EVP 比较 128 B/16 KiB 的三组成本中位数，随后进程内只读复用。大包 AES 成本低于 ChaCha 的 85%，且小包成本低于其 110%，才前置 AES-256-GCM。库提供者不可用或没有清晰收益时沿用库默认；未知环境值也沿用库默认。原有固定主机公钥、认证、握手、背压、完整性和 EOF 不变。OpenSSL 负责 CPU/OS 指令分派，支持何种 AES-NI/PCLMUL、ARM AES/PMULL 实现取决于目标 OpenSSL 构建；没有全局 `-march=native`、AVX2 或 AVX512 要求。

EVP 的 ChaCha AEAD 结构与 OpenSSH 的结构不同，探测只是保守启发式，实际收益由下面的原生转发验证。探测只衡量本机成本，不知道异构对端 CPU 的速度，不能保证任意 CPU 配对都最优。Windows 正常硬件下每进程首次探测为 1.509–2.334 ms，Linux 为 2.390–3.162 ms；这些是本次环境的观测值，不是时延上限。

`BUGGCRAFT_SSH_CIPHER_POLICY=auto|library|aes-gcm|chacha` 在进程第一次连接前设置；后两项是偏好，仍可协商回退。`library` 可以恢复旧顺序。密码和密钥仍完全由原库管理。对已建立会话或 P2P 的 DTLS 载荷不修改算法；这里的吞吐结论适用于 SSH relay。

## 环境和负载

| 环境 | CPU / 构建 | 密码库 |
| --- | --- | --- |
| Windows x64 | i9-10850K，10 核/20 线程；MinGW GCC 15.2，Release/LTO | OpenSSL 3.5.2，libssh 0.12.2 |
| Ubuntu Linux x64 | EPYC 7K62，4 vCPU；GCC 13，Release/LTO | OpenSSL 3.0.13，libssh 0.12.2 |

两台机器分别使用回环独立测试端口：原生节点 + 1 个原生房主桥 + 3 个原生访客桥。每访客两条不限速 64 KiB 大流，另有 112 B 小包探测、每 0.5 秒短连接/房间控制请求。大流逐块比较全部回声字节，完成后检查双向 EOF；小包在大流同时运行时测量。玩家 0 的大流可高度压缩，其余为固定随机块。每轮持续 30 秒，每种配置三轮，第二轮反转顺序；额外 pilot 不进入统计。发生器关闭 asyncio debug，常规回归仍保留 debug。

吞吐是各访客已验证应用回声数据合计/实测负载时间，每次往返计一次数据；一次回声经过多段转发/加密，不能把数值直接换算成网卡线速。P99 每轮先取各玩家 P99 的最大值，再取三轮中位数。CPU 为每 5 秒采样得到的所有原生进程 CPU 时间/GiB 应用回声；包含建立连接、日志和收尾阶段，且可能漏掉最后不足一个采样间隔的 CPU，适合比较趋势，不是精确单包成本。

实际经过 Minecraft 握手准入，之后是合成游戏载荷，不是完整 Minecraft 协议活动或 GUI 帧率测试。没有把同机回环写成公网、LAN 或 P2P 结果。本次没有出现需要点击的防火墙弹窗，也没有关闭防火墙；回环成功不能代替跨机器入站规则验收。Linux 只在隔离目录构建/运行，没有替换线上服务。

补充直接公网完整性验收：使用本轮二进制，Windows CLI 访客↔Linux SDK 房主、Linux CLI 访客↔Windows SDK 房主，均实际走 relay，分别完成 4 MiB 随机载荷的 SHA-256 与 EOF 校验，耗时 5.281/5.545 秒。记录确认公网节点 TCP 可达，没有使用 SSH 数据隧道代替该结果。这里只有双向功能验收，没有公网三轮 ISA A/B，不能把回环吞吐增幅套到公网。原始记录为 `wan-direct-auto-0.json`。

新 auto 与同算法 crypto-fixed 的中位吞吐相差 Windows 5.58×、Linux 10.33×；无加速时允许自动选 ChaCha，相比继续使用软件 AES 分别为 3.22×、4.08×。这些是人为屏蔽 OpenSSL 能力的对照，不能等同于某款真实旧 CPU，也不表示整个程序不再使用 SIMD。

新 auto 没有显示出新增字节 SIMD 对游戏转发的收益。小包 P99 改善有限，Linux 范围仍重叠，不能宣布公网延迟按吞吐比例下降。本轮正常配置体现的是 CPU 吞吐余量增加；CPU/RSS 也没有出现内存换吞吐的明显增长。Windows 旧/新原生 RSS 峰值中位数为 151.82/152.57 MiB，Linux 为 143.82/142.49 MiB。全部上述 30 个实测案例校验通过，没有大块间隔超过 100 ms 的记录。

## 复现和覆盖

先保留修改前完整运行目录，再按构建指南构建 Release，准备 Python 测试依赖。Windows 将桥/节点运行依赖加入 PATH；Linux 按共享库布局设置 LD_LIBRARY_PATH。仓库根目录执行：

```bash
python scripts/benchmark_forwarding.py --rounds 3 --seconds 30 \
  --baseline-core /path/to/before/buggcraft-core \
  --baseline-bridge /path/to/before/buggcraft-bridge \
  --output validation-artifacts/game-forwarding
python scripts/benchmark_forwarding.py --profiles baseline auto --compression auto \
  --baseline-core /path/to/before/buggcraft-core \
  --baseline-bridge /path/to/before/buggcraft-bridge \
  --output validation-artifacts/game-forwarding-default
```

原始 JSON、每轮日志、进程资源采样、修改前二进制和源码快照位于 `validation-artifacts/game-forwarding-20261110/`；每个结果包含被测节点/桥 SHA-256。`scripts/benchmark_forwarding.py` 只编排既有 `bridge_soak.py` 与 `BridgeTests`；掩码复用 `benchmark_cpu.child_environment`，仅作用于原生子进程，不改变 Python 发生器或系统环境。方法与 DOM 清单、生命周期契约及开发 Skill 已同步；本轮无 UI/DOM 改动。

Windows/Linux x64 有实机转发性能。ARM64/macOS 没有实机数据，不能声称已验证其性能；此前 ARM64 QEMU 的编码验证也不能替代本轮转发实测。新策略没有新增架构专用汇编，其他可构建架构继续使用原库和通用回退。未来应补异构对端、真实 ARM/macOS、带宽/丢包/RTT 受限公网与原版游戏活动的独立矩阵。

新增策略已通过 MSVC x64 单文件编译；ARM64 GCC 交叉编译并在 QEMU 下执行策略与分支检查，正常/`OPENSSL_armcap=0` 均完成。两项仅分别证明该模块可编译/可执行，不等于完整 SDK 跨平台构建或性能。受限算法服务器夹具验证仅允许 ChaCha 或 AES-CTR 时的固定公钥、认证、目录 RPC 和实际协商结果；游戏载荷、EOF、P2P/中继混用、故障回退和 CLI/SDK 互通通过原生节点夹具验证，不能把旧 Python 夹具的控制测试写成旧节点完整游戏验收。

最终验收：Windows/Linux 的正常与屏蔽新增 SIMD/OpenSSL 能力两种配置各通过 4/4 CTest；Windows 41 项节点/桥/SDK 集成全部通过；Linux 同一套 41 项中 38 项通过、3 项跳过。之后安装独立运行包，Linux 的重定位项另测通过，剩余两项缺旧启动器源码，仍不算通过；Windows 也对本轮新运行包单独复测重定位通过。回归含压缩尾帧、原始帧边界、固定公钥拒绝、断流回退、其他玩家继续转发、P2P/relay 混用、CLI↔C ABI，以及文件/游戏并行。普通回归带 asyncio debug，其延迟输出不进入性能表。

本轮新 Windows 运行包安装在 `validation-artifacts/game-forwarding-20261110/runtime-after/`，Linux 在隔离目录 `game-runtime-after/`，均通过包含中文/空格路径、无关工作目录和干净 PATH 的加载检查。本轮没有重启用户正在运行的启动器，没有替换生产节点；交付的是源码、构建结果和验证过的独立运行包。
