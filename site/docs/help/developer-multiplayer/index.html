联机接入：统一服务、节点与 C ABI SDK

按实际接口接入账号授权、好友邀请和房间调度，游戏数据复用同一份原生桥。

更新于 2026-11-11 · BUGG 项目维护者

本篇目录先明确三个角色检查控制协议入口设备授权与控制身份好友与房间复用原生桥的内存与并发契约

01先明确三个角色

统一服务管理账号、设备授权、好友、在线与节点分配；节点负责房间连接和转发；桥与 SDK 运行在玩家电脑上。游戏字节不经过统一服务。

客户端使用统一服务的浏览器设备授权，不在节点实现第二个登录入口。自建服务通过配置 origin、CA 和签名公钥接入，不分发管理员令牌或中心私钥。

02检查控制协议入口

/v1 操作使用 HTTPS POST 与 JSON 对象；有权限的操作在 Authorization: Bearer 请求头传入对应的短期运行授权。HTTP 与 WSS 调用同一个领域入口，不能把管理员密钥放在客户端。

curl --fail --silent --show-error -X POST \
  -H "Content-Type: application/json" \
  --data '{}' https://node.bugg.icu/v1/health

03设备授权与控制身份

  1. 调用 /api/launcher/start，提交本机设备公钥与可辨认的设备名；在浏览器完成账号登录并确认。
  2. 设备对轮询挑战签名，经 /api/launcher/poll 取得授权与控制服务元信息。保留并校验服务 CA 和签名公钥。
  3. 使用证书、设备委托和设备私钥挑战调用 /v1/identity/challenge、identity/prove，取得玩家运行授权。刷新与撤销沿用同一套设备协议。
记住这一点

签名字段和规范化字节必须按源码协议处理。优先使用原生桥现有实现，不在每种语言中各造一套认证。

04好友与房间

/v1/social/state 取得好友与邀请；social/apply 提交带 event_id 的操作，social/inbox 与 social/ack 区分已持久化、已送达和已读。

placement/candidates 返回有界候选；placement/reserve 原子预留容量。好友加入固定 room_id / epoch 所属节点，不能把加入已有房间改成重新按地区分配。节点使用 placement/confirm 确认与续租，结束后 release。

05复用原生桥的内存与并发契约

SDK 入口为 buggcraft_bridge_create、buggcraft_bridge_call、buggcraft_bridge_free 与 buggcraft_bridge_destroy。请求使用 UTF-8 JSON-RPC，最大 8192 字节；业务错误仍需检查响应 JSON。

响应内存由原库释放；同一句柄串行调用，不与 destroy 竞争。销毁所有句柄并释放响应后再卸载库。CLI 与 C ABI 共用 Rpc / ControlClient，不复制转发或调度规则。
